# CLAUDE.md

Guidance for Claude Code when working in this repo.

## What this repo is

Prodigy game knowledge base + procedural skill reference, packaged as a [qmd](https://github.com/tobi/qmd)-backed Docker image that exposes a stdio MCP server. Starts with Math Game; Game Island joins next. Shared across product, design, and data working on games.

The repo is a prototype — the eventual org knowledge infrastructure will likely absorb pieces of this. The goal is to iterate quickly and produce foundation pieces and lessons. Architecture decisions are reversible by design.

## Two trees, two cadences

```
knowledge/         ← factual reference (slow PR cadence)
skills/            ← procedural craft (weekly arc→review→PR cadence)
```

### `knowledge/` — factual reference

Slow-changing, PR-reviewed. One file per page, organized by content type:

- `knowledge/event-schemas/` — game event schemas (analytics, telemetry, tracking)
- `knowledge/game-design/` — design docs, glossaries, core loops
- `knowledge/session-profiles/` — player/session profile documents
- `knowledge/INDEX.md` / `knowledge/pages.json` — regenerated by `tools/build_index.py`

Indexed as the qmd collection `kb`.

### `skills/` — procedural craft

Per-workflow directories. Each skill is one self-contained subtree:

```
skills/<name>/
├── SKILL.md          ← entry prompt (the thing the user invokes)
├── reference/        ← templates, heuristics, examples (INDEXED as skill-<name>)
├── arcs/             ← per-execution observations (NOT indexed)
└── reviews/          ← weekly review notes (NOT indexed)
```

Indexed as the qmd collection `skill-<name>` (one per skill, derived from directory name). Adding a new skill is purely additive — drop the directory, rebuild, the Dockerfile picks it up via shell glob.

## Frontmatter contract

Every `*.md` page under `knowledge/` and `skills/<name>/reference/` SHOULD start with YAML frontmatter:

```yaml
---
title: Progression Event Schema
type: event-schema
owner: data-team
last_modified: 2026-04-28
status: stable
related:
  - knowledge/game-design/progression-loop.md
---
```

Fields:

| Field | Required | Notes |
|---|---|---|
| `title` | yes | Display name; falls back to filename stem if missing. |
| `type` | recommended | Free-form. Used to group in `INDEX.md`. Examples: `event-schema`, `glossary`, `design-doc`, `session-profile`, `template`, `heuristics`. |
| `owner` | recommended | Team or individual. Surfaces in INDEX. |
| `last_modified` | recommended | ISO date (`2026-04-28`) preferred; `Apr 28, 2026` also accepted. |
| `status` | optional | `draft`, `stable`, `deprecated`. |
| `related` | optional | List of `- ` prefixed paths to related pages. |

The frontmatter parser is hand-rolled in `tools/build_index.py` (no PyYAML dep) — keep the format simple: scalars and `- `-prefixed lists only. If you add a new field, extend `parse_md` accordingly.

## The arc lifecycle

Skills evolve through real usage, not speculation. Every skill execution writes an arc, and arcs are reviewed weekly to produce skill PRs.

```
EXECUTION
  Skill runs (drafts a DDD, writes a schema, etc.).
  Last step of the skill: write skills/<name>/arcs/<YYYY-MM-DD>_<topic>.md.
       │
       ▼
CAPTURE
  Arc lives on a feature branch (or shared inbox branch).
  Arcs are PROPOSALS, not truth — never indexed.
       │
       ▼
WEEKLY REVIEW
  A reviewer reads the week's arcs, triages each:
    • procedural fix    → PR to SKILL.md or reference/
    • domain fact       → PR to knowledge/
    • duplicate / noise → close
    • needs discussion  → tag for sync
  Review captured as skills/<name>/reviews/<YYYY-MM-DD>.md.
       │
       ▼
MERGE
  PRs merged → next executions pick up the improved skill on rebuild.
```

### Arc file shape

```markdown
---
date: 2026-04-28
skill: ddd-drafting
domain: math-game
user: stepan
status: proposed          # proposed | accepted | rejected
target: skill             # skill | knowledge | both
---

## What worked
- ...

## What didn't
- ...

## Proposed change
- ...
```

Keep arcs cheap to write. If the form is more than 4 sections, it dies.

## Pipeline

`tools/build_index.py` is the routinely runnable piece:

```sh
# After hand-editing a knowledge page that changes title / last_modified / structure:
uv run tools/build_index.py     # rewrites knowledge/INDEX.md + pages.json
```

It's pure post-processing over `knowledge/`. Skills don't get an INDEX.md (their `reference/` is small and the user navigates by filename).

## Architecture notes that aren't obvious from a single file

- **Multi-collection qmd index, one image.** The Dockerfile's index stage registers `kb` (over `knowledge/`) plus one `skill-<name>` collection per directory under `skills/*/reference/`. Adding a skill = drop a directory; no Dockerfile edit. The shell glob in the index stage (`for skill_ref in /home/qmd/skills/*/reference; do`) is the discovery mechanism.
- **Arcs and reviews are NOT indexed by design.** They are proposals; allowing them to ground future skill executions would let unreviewed claims pollute retrieval. The `.dockerignore` excludes `skills/*/arcs/` and `skills/*/reviews/` from the build context, and the Dockerfile's `qmd collection add` only points at `reference/`. The full `skills/` tree is still copied into the runtime image so files are filesystem-readable from inside the container — they just aren't searchable.
- **Folder structure is the category.** Unlike kb-infra (which derives categories from Confluence breadcrumbs in frontmatter), kb-game uses the first folder under `knowledge/` (e.g. `event-schemas`, `game-design`) as the category. `build_index.py` reads it from the path, not the frontmatter.
- **Frontmatter is the contract.** `tools/build_index.py` parses `title`, `type`, `owner`, `last_modified`, `status`, `related`. If you add a frontmatter field, extend `parse_md` accordingly and keep the format simple.
- **Embedding retry pass is mandatory.** CPU `qmd embed` drops ~1-2% of chunks with "Session expired" errors. The Dockerfile runs `qmd embed --max-docs-per-batch 30` twice for that reason — do not collapse to one call.
- **No LFS yet.** `knowledge/` is text-only at start. If we add binaries (design mocks, screenshots), set up LFS at that point — kb-infra's `.gitattributes` rule (`knowledge/attachments/** filter=lfs`) is the precedent.

## Editing flow

- Hand-edits to `knowledge/**/*.md` and `skills/*/reference/**/*.md` are the norm. PR them.
- After any edit that changes a title, `last_modified`, or moves a file under `knowledge/`, rerun `uv run tools/build_index.py`.
- Adding a new skill:
  1. `mkdir -p skills/<name>/{reference,arcs,reviews}`
  2. Write `skills/<name>/SKILL.md` (entry prompt)
  3. Add at least one `*.md` under `skills/<name>/reference/`
  4. Optionally add `.gitkeep` to empty `arcs/` and `reviews/` to track them
  5. Rebuild the image — the new `skill-<name>` collection is discovered automatically
- Adding a new arc: write directly to `skills/<name>/arcs/<YYYY-MM-DD>_<topic>.md`. No tooling needed.

## Not in scope (yet)

- ECR / shared image distribution. Local builds only during prototype.
- Plugin packaging for skills.
- Automated arc → review pipeline. Reviews are a manual weekly cadence for now.
- GPU-based embedding. CPU embed time is acceptable at current corpus size.
- Cross-skill shared content (`skills/_shared/`). Add only if duplication actually hurts.
